# Acme — маркетинговый сайт. Объяснение для человека

Этот файл написан так, чтобы его понял любой, кто открыл репозиторий впервые: и разработчик, и маркетолог, и менеджер. Без жаргона там, где без него можно обойтись.

Английская версия — [README.md](README.md).

---

## 1. Что это вообще

Это сайт компании Acme — тот, что продаёт AI-агентов. Раньше он жил на WordPress. Здесь он пересобран с нуля на другом стеке.

Главная идея, ради которой всё затевалось: **страницы сайта должны собираться из готовых кубиков, а не верстаться каждый раз заново.** Кубик называется «блок» — это, например, первый экран, сетка карточек, таблица цен, FAQ, блок отзывов. Сейчас таких блоков 47 штук.

Из этого следует вторая идея: если страница — это просто список блоков и текст в них, то её может собрать не только дизайнер с верстальщиком, но и человек, который просто написал, что хочет получить. Или AI по его тексту. Этому посвящена вторая половина документа.

---

## 2. Из чего состоит

Три программы, которые работают одновременно и разговаривают друг с другом.

**Payload CMS** (`apps/cms`) — админка и база. Здесь редакторы правят тексты, картинки и страницы. Работает на порту **3000**. Под ней база данных PostgreSQL, где всё физически хранится.

**Astro** (`apps/web`) — сам сайт. Берёт контент из CMS и превращает в HTML, который видит посетитель. Работает на порту **4321**.

**Form API** — маленький сервис, принимающий отправку форм с сайта. Порт **8787**.

Как они связаны:

```
PostgreSQL  →  Payload CMS  →  REST API  →  Astro  →  HTML в браузере
  (данные)      (:3000)      (/api)       (:4321)
```

Читать так: данные лежат в Postgres. Payload даёт к ним доступ через админку и через API. Astro ходит в этот API по адресу `http://localhost:3000/api`, забирает страницы и рисует их.

**Важная деталь, на которой все спотыкаются:** в адресе API обязателен хвост `/api`. Просто `http://localhost:3000` не сработает — Astro не найдёт контент.

## 3. Как устроена страница

Каждая страница — это запись в базе, у которой есть маршрут (`/ai-receptionist/`), заголовок, SEO-поля и **список блоков**. Блок — это объект с типом и содержимым:

```json
{
  "type": "hero",
  "eyebrow": "AI Receptionist for Cleaning Companies",
  "title": "Turn Every Missed Call ||{{ Into Booked Jobs }}",
  "description": "Одно предложение о том, что делает агент.",
  "primaryAction": { "label": "Get Started Free", "href": "/signup" }
}
```

Дальше цепочка простая:

1. Посетитель открывает `/ai-receptionist/`.
2. Файл `apps/web/src/pages/[...slug].astro` ловит любой маршрут и спрашивает у CMS: что лежит по этому адресу?
3. CMS отдаёт список блоков.
4. Файл `apps/web/src/components/BlockRenderer.astro` — **диспетчер**. Он смотрит на `type` каждого блока и вызывает нужный компонент: `hero` → `HeroBlock.astro`, `faq` → `FaqBlock.astro`, и так далее.
5. Компонент рисует HTML.

Это и есть ответ на вопрос «как оно вызывает функции»: **по полю `type`**. Никакой магии, обычная таблица соответствий «имя блока → компонент».

Два маркера, которые можно писать прямо в заголовках:

- `{{ слово }}` — выделить слово градиентом;
- `||` — принудительный перенос строки.

Посмотреть все 47 блоков живьём: `http://localhost:4321/blocks` и далее `/blocks-2` … `/blocks-9`.

## 4. Первый запуск

Нужен **Node.js 22.13+** и **PostgreSQL** (`brew install postgresql@15`). Docker не нужен.

```sh
npm run setup   # один раз: зависимости, своя база в .pgdata, .env-файлы, контент и все генерации
npm run dev     # каждый раз: CMS, сайт и форм-API
```

`npm run setup` можно запускать повторно — он ничего не ломает. Если порт 5432 уже занят другим Postgres: `PGPORT=5544 npm run setup`.

После запуска:

- админка — http://localhost:3000/admin, логин `admin@aa.aa`, пароль `admin` (только для локальной разработки);
- сайт — http://localhost:4321

Если Postgres остановился (после перезагрузки): `LC_ALL=en_US.UTF-8 /opt/homebrew/opt/postgresql@15/bin/pg_ctl -D ./.pgdata start`.

Проверка, что всё правильно: в логе запуска должна быть строка

```
[content] Loaded 336 pages from Payload at http://localhost:3000/api
```

Картинки старого контента в пример не входят (медиа живут вне репозитория), поэтому часть изображений на старых страницах будет пустой. Сгенерированные страницы и блоки это не затрагивает.

### Альтернатива: всё в Docker

```sh
cp .env.docker.example .env.docker
npm run docker:local:setup   # один раз
npm run docker:local:up
```

Внутри Docker адрес API другой — `http://cms:3000/api`, потому что сервисы видят друг друга по именам. Он уже прописан в `docker-compose.local.yml`, менять не нужно.

```
  instructions/  закон композиции: какой блок для чего

  source/     артефакты миграции со старого сайта

```

### Про `packages/blocks` — почему это главное место

Здесь лежит общий словарь, на который опираются и CMS, и сайт, и AI:

- **`schemas.ts`** — какие поля есть у каждого блока и что считается валидным. Если JSON не проходит схему, он не попадёт в базу.
- **`registry.ts`** — **каталог блоков**: у каждого записаны роль, идеальное количество элементов и `aiGuidance` — подсказка, когда этот блок брать, а когда нет.
- **`categories.ts`** — группировка блоков.
- **`payload.ts`** — перевод между форматом Payload и внутренним форматом.

Запомните одно: **`registry.ts` — это глаза системы.** Блок может существовать в схеме, иметь готовый компонент и стоять на живых страницах, но если его нет в реестре — генератор страниц его не увидит и будет считать, что такого блока не бывает. Ровно на этом система один раз обожглась (разбор — [docs/page-generation-v3](docs/page-generation-v3/README.ru.md)).

## 6. AI-система генерации страниц

Это вторая половина проекта. Задача: маркетолог пишет текстом, что за страница нужна, и получает готовый черновик в админке. Без дизайнера и верстальщика в середине.

### Два трека, и разница между ними принципиальна

**Трек A — текст уже есть.** Команда маркетинга пишет текст лендингов своими скиллами в Claude, и у них зрелый свод правил: запрещённые слова в трёх уровнях строгости, пять блоков «пиши как человек, а не как машина», зафиксированные факты о продукте, лимит длины на каждое поле и данные по болям отраслей со ссылками на источники. На выходе — документ с нумерованными секциями (`## S1 - Hero`, `## S4 - Pain Points`), который кладут в батч страницы как `lp.md`.

На этом треке **текст — это вход, а не черновик.** Система переносит эти слова в секции страницы байт в байт. Она не сокращает их, не меняет голос, не правит пунктуацию и не «доводит». Если строка не влезает в секцию, для которой написана, система не правит строку — она выдаёт **fit-report**: измеренную длину, настоящий предел секции и варианты, один из которых всегда «взять другую секцию». Решает всегда автор.

Это не обещание, а проверка: `npm run qa:copy-fidelity` сравнивает каждую строку `lp.md` с собранной страницей и падает на любом расхождении, вплоть до потерянной запятой.

**Трек B — текста нет, есть только задача.** Тогда текст пишет сама система — и держит тот же свод правил, потому что человека-автора у этого текста нет.

### Как вызывать

В Claude Code внутри репозитория:

```
/create-page      создать страницу из текста
/create-block     спроектировать новый блок (только если без него никак)
```

Дальше система задаёт несколько вопросов человеческим языком: про что страница, для кого, что обещаем, куда ведём, нужна ли ссылка в меню.

### Что происходит внутри

**Фаза 0 — проверка окружения.** Живы ли CMS и сайт, из правильного ли места берётся контент.

**Фаза 1 — бриф.** Вопросы, выбор маршрута. Маршрут обязательно проверяется по трём источникам: живая CMS, снапшот `data/cms/pages.json` и похожие адреса-синонимы. Потому что локальная база бывает старее снапшота, и «в CMS нет» ещё не значит «страницы не существует».

**Фаза 2 — сборка.** Система читает каталог блоков, закон композиции, схемы, компоненты и одну-две живые страницы того же типа как образец. Затем заполняет таблицу: на каждую секцию — какой блок берём и почему.

Здесь работает **правило переиспользования**. Новый блок — исключение. Чтобы его создать, нужно выполнить все три условия сразу:

1. ни один существующий блок не закрывает роль этой секции;
2. секция приносит новый **механизм** — интерактивность, структуру данных, способ подачи (другие иконки или другой фон механизмом не считаются);
3. блок пригодится ещё минимум на двух будущих страницах.

Максимум один новый блок на страницу.

**Фаза 2.5 — текст.** Три режима, и режим выбирается по тому, откуда текст пришёл, а не по тому, насколько он хорош.

- **Перенос дословно.** Трек A. Каждое поле, у которого есть соответствие в `lp.md`, копируется байт в байт. Единственное, что система имеет право добавить, — разметку, которая нужна рендереру, и только там, где документ обозначил намерение: градиентное выделение, принудительный перенос строки. Ни одно слово не меняется.
- **Дозаполнение служебных полей.** Секциям нужны поля, которых в текстовом документе нет: подписи шагов вида «Days 1-3», выбор иконок, описания картинок, если автор их не дал. Их пишет система — и перечисляет каждое в отчёте батча под заголовком «Written by the pipeline», чтобы автор подтвердил или заменил. Никогда не заголовок, не описание и не подпись кнопки: если их нет, это пункт fit-report, а не дозаполнение.
- **Система пишет для себя.** Демо-контент нового блока и витрина блоков. Авторского текста там нет по определению, и только здесь по-прежнему запускается агент-копирайтер — с чистой головой и только правилами письма, потому что агент, который одновременно держит в голове схемы, ловушки компонентов и проверки сдачи, пишет мёртвым языком.

Свод правил — маркетинговый, перенесён в репозиторий со строкой версии, чтобы копии не разъезжались молча. Поверх него одно дополнение с нашей стороны: слой правил стандарта **ASD-STE100 (Simplified Technical English)** — один термин на одно понятие, не больше 20 слов в предложении, активный залог с названным действующим лицом, настоящее время, не больше трёх существительных подряд. И оговорка, которая главнее ясности: из секции нельзя вычищать обещание, иначе страница превращается в инструкцию и перестаёт продавать.

**Фаза 3 — проверка.** Прогон валидатора вхолостую, пока не станет чисто, плюс гейт по тексту: `npm run qa:copy` проверяет всё из свода правил, что может решить скрипт, — запрещённые слова, тире, длины, зафиксированные подписи кнопок, зафиксированные названия тарифов, повторное использование одной цифры, сертификаты, которых у компании нет, и любую цифру, которой нет ни в файле разрешённых фактов, ни в брифе. Он сообщает и никогда не правит, а в отчёте прямо перечислено, чего он проверить не может, — чтобы его не приняли за всю работу.

**Фаза 4 — импорт и приёмка.** Страница заливается **черновиком**, снимаются скриншоты на десктопе и мобильном, прогоняются проверки, а затем — **отдельный агент-ревьюер**, который страницу не собирал и ищет, что с ней не так. Это не формальность: на каждом прогоне ревьюер находил блокеры, которые самопроверка пропустила.

**Фаза 5 — сдача.** Ссылки и список хвостов. **Публикация — всегда действие человека** кнопкой в админке.

### Где лежат правила

| Файл | Что в нём |
|---|---|
| `.claude/skills/create-page/SKILL.md` | сценарий создания страницы, оба трека |
| `.claude/skills/create-block/SKILL.md` | сценарий создания нового блока |
| `ai/instructions/page-compose.md` | какой блок для чего, арка страницы, политика CTA, политика переиспользования |
| `ai/contracts/copy-rules.md` | **правила письма — единственный свод в репозитории.** Перенесён из скилла маркетинга, со строкой версии |
| `ai/contracts/copy-data.md` | какие факты странице разрешено утверждать: боли по отраслям со ссылками, стеки интеграций, порядок каналов, стоимостные якоря, утверждённые определения категорий, список конкурентов |
| `ai/contracts/lp-handoff.md` | как текст маркетинга становится страницей: три режима, fit-report и какая секция ложится в какой блок |
| `ai/contracts/block-contracts.md` | контракты блоков и общие правила оформления |
| `ai/marketing-skills/` | то, что уходит обратно в маркетинг: надстройка к их скиллам плюс короткий список правок |
| `ai/prompts/copy-refiner.md` | промпт агента-копирайтера — теперь только для текста, который система пишет себе |
| `ai/checklists/page-generation-review.md` | чеклист приёмки |

Одно осознанное решение в этой таблице: правила существуют **один раз**. Больше нигде в репозитории правило письма не повторяется, всё ссылается на `copy-rules.md`. Маркетинг научился этому дорогой ценой: в каждый их скилл была вложена копия общего свода, копии устарели, и из-за этого три неверных правила прожили целую версию.

## 7. Команды

Всего в проекте 87 скриптов. Вот те, которыми реально пользуются.

### Запуск и сборка

| Команда | Что делает |
|---|---|
| `npm run dev` | поднять всё сразу: CMS, сайт, форм-API |
| `npm run dev:cms` | только CMS |
| `npm run dev:web` | только сайт |
| `npm run build` | собрать всё для продакшена |
| `npm run typecheck` | проверка типов |
| `npm run lint` | линтер |
| `npm run format` | отформатировать код |

**Отдельно запомнить:** после **любого** изменения структуры блоков в Payload нужно запускать CMS так:

```sh
PAYLOAD_DB_PUSH=true npm --workspace @acme/cms run dev
```

Иначе база не узнает о новых полях, и они будут молча теряться. Важно: такие изменения должны быть **только добавляющими**. Если в одном заходе что-то добавить и что-то удалить, миграция задаст интерактивный вопрос, на который в автоматическом режиме некому ответить.

### Контент

| Команда | Что делает |
|---|---|
| `npm run cms:upsert -- --file <файл> --write false` | проверить файл со страницами, ничего не записывая |
| `npm run cms:upsert -- --file <файл> --write true` | залить страницы в CMS |
| `npm run cms:export` | выгрузить контент из CMS |
| `npm run cms:snapshot` | сделать снапшот |
| `npm run cms:navigation` | обновить меню сайта |
| `npm run cms:media-usage` | отчёт, какие картинки где используются |

Ключ `--write false` — это «примерка»: система скажет, всё ли в порядке, но ничего не изменит. Всегда начинайте с неё.

Импортёру нужен токен доступа:

```sh
PAYLOAD_API_TOKEN=<токен> npm run cms:upsert -- --file <файл> --write true
```

**Осторожно:** импортёр ищет совпадение по адресу страницы **внутри указанной коллекции**. Если ошибиться коллекцией, вместо обновления получится дубликат на живом адресе.

### Проверки качества

| Команда | Что проверяет |
|---|---|
| `npm run qa:block-registry` | что каталог блоков, схемы и компоненты совпадают |
| `npm run qa:copy` | правила письма по батчу страницы. Добавь `--brief <батч>/brief.md`, иначе любая цифра из брифа читается как выдуманная. `--legacy` превращает в обзор, который никогда не падает |
| `npm run qa:copy-fidelity` | что текст автора дошёл до страницы без изменений, и какие строки на странице автор не писал |
| `npm run qa:keyword-collision` | не занят ли маршрут или ключевик другой страницей |
| `npm run qa:links` | битые ссылки |
| `npm run qa:media` | битые картинки |
| `npm run qa:seo` | SEO-поля |
| `npm run qa:no-inline-block-styles` | что стили не написаны прямо в компонентах |
| `npm run qa:no-hotlinks` | что нет ссылок на чужие домены (нужна сборка) |
| `npm run qa:content` | здоровье контента |
| `npm run qa:launch-readiness` | сводная готовность к запуску |

Две проверки — `qa:block-root-attrs` и `qa:html-structure` — ждут статическую сборку, а сайт работает динамически. Они выдают сотни сообщений `missing-built-html`, и это не ошибки, а особенность. Не пугайтесь.

`npm run ai:block-catalog` пересобирает человекочитаемый каталог блоков, который лежит внутри надстройки для маркетинга. Запускай после добавления блока, иначе маркетинг продолжит писать под устаревший список того, что сайт умеет рендерить.

### Миграция со старого сайта

Группа команд `migrate:source:*` — перенос данных с WordPress. Это одноразовая история, в повседневной работе не нужна. Старый сайт и дамп базы здесь только как **источник для импорта**: новые схемы, компоненты и всё остальное от WordPress не зависят.

## 8. Как обычно работают

**Поправить текст на существующей странице.** Через админку http://localhost:3000/admin. Никакого кода.

**Создать новую страницу.** Команда `/create-page`, ответить на вопросы, дождаться черновика, посмотреть, опубликовать кнопкой в админке.

**Поправить внешний вид блока.** Стили блока лежат в `apps/web/src/styles/blocks/_<имя>.scss` и подключаются внутри компонента. Инлайновых стилей и тегов `<style>` в компонентах быть не должно — за этим следит `qa:no-inline-block-styles`. Цвета, размеры и отступы берутся из токенов в `packages/styles`, а не пишутся числами.

**Добавить новый блок.** Команда `/create-block`. Но сначала честно проверьте, не закрывает ли задачу существующий блок с другим содержимым — в девяти случаях из десяти закрывает. Регистрация нового блока — это десять шагов в разных файлах, и пропуск любого приводит к тому, что блок либо не проходит валидацию, либо не рисуется, либо невидим для генератора.

## 9. Грабли, на которых теряют время

- **Черновики не открываются на сайте** — отдают 404. Чтобы посмотреть глазами, страницу надо временно опубликовать, а потом вернуть в черновик.
- **Блок `hero`:** если заполнено поле `eyebrow`, то именно оно становится заголовком первого уровня `<h1>`, а видимый заголовок опускается до обычного абзаца. Это сделано намеренно — так ключевое слово попадает в `<h1>` на отраслевых страницах. Но проверять итог нужно в готовом HTML, а не в данных.
- **Блоки `faq` и `security`:** поля `title` и `titleGradient` рисуются двумя отдельными строками, причём вторая — вне заголовка. Если ключевое слово нужно в заголовке, оно должно быть в первом поле.
- **Блок `logo-grid`** выбрасывает элементы, у которых заполнен только текст без ссылки или картинки: импортёр считает их недозаполненными.
- **Блок `channels-grid`** без своих картинок подставляет чужие заглушки. Картинки задавайте всегда.
- **Фирменный градиент** проходит через почти чёрный цвет и пропадает на тёмных панелях. На таких блоках его переопределяют сплошным цветом.
- **Никогда не включайте автопрокрутку** там, где она меняет читаемый текст, если рядом нет видимой кнопки остановки. Это требование доступности, а не вкусовщина.
- **Скриншоты** снимайте через Playwright из корня репозитория и обязательно прокручивайте страницу с паузами: иначе анимации появления и ленивые картинки не успеют проявиться, и получите пустые блоки.

## 11. Превью-окружение и деплой

У проекта есть общее превью-окружение в DigitalOcean:

- сайт — `https://preview.example.com`
- админка — тот же адрес с `/admin`
- API — тот же адрес с `/api`

Из чего оно состоит: Astro и Payload как два отдельных сервиса App Platform, собранные из образов в реестре контейнеров; управляемая база PostgreSQL; бакет Spaces для медиафайлов; HTTPS и маршрутизация средствами платформы, без отдельного Nginx; отправка форм напрямую в Formspree, без сервиса форм.

Важное свойство: **публикация контента в Payload не пересобирает сайт.** Astro читает CMS в момент запроса и держит короткий кеш. То есть опубликовали — и через несколько секунд видно, без деплоя.

Идентификаторы проекта, доступы к базе, к Spaces и к превью-админке лежат локально в `.env.digitalocean.local`. Этот файл в Git не попадает и попадать не должен.


## 12. Формы

Формы на сайте отправляются только на адрес из `PUBLIC_FORM_ENDPOINT` (локально это `/api/forms/submit`). Сервис форм сохраняет каждую принятую заявку в Payload и при необходимости пересылает нужные типы в Formspree.

Что нужно настроить: одинаковый `FORM_SUBMISSION_SECRET` в окружении CMS и сервиса форм, и `FORM_PAYLOAD_API_URL`, указывающий на CMS. Адреса Formspree живут **только** в серверных переменных `FORMSPREE_ENDPOINT_*` и никогда не попадают в браузер.

## 13. Payload MCP для Codex

Конфигурация MCP указывает Codex на `http://localhost:3000/api/mcp`. Порядок: создать уникальный `PAYLOAD_MCP_API_KEY` в `apps/cms/.env`, завести соответствующий ключ в админке (**Payload Admin → MCP → API Keys**) и отдать его новым процессам Codex:

```sh
launchctl setenv PAYLOAD_MCP_API_KEY "$(awk -F= '/^PAYLOAD_MCP_API_KEY=/{print $2}' apps/cms/.env)"
```

После этого Codex нужно перезапустить. Локальному ключу стоит выдавать доступ только к тем коллекциям и операциям, которые реально нужны.

## 14. Правила репозитория

- Не коммитить сырые дампы продакшена и любые секреты.
- Коммитить только очищенные производные артефакты импорта.
- Для сгенерированного контента использовать `cms:upsert`, а не писать отдельные скрипты заливки под каждую страницу.
- Визуальное сравнение делать детерминированными проверками через Playwright, и только спорные случаи отдавать на разбор AI.
