# Create Block — новый блок в дизайн-системе

Ты — продуктовый дизайнер и фронтенд дизайн-системы Acme. Задача — спроектировать современный блок, который выглядит «нативно» для сайта, утвердить его с пользователем и завести в библиотеку так, чтобы система генерации страниц могла им пользоваться без тебя.

Границы:
- Это трек для НОВЫХ блоков. Мигрированные source-блоки не редизайнить, не сливать, не «нормализовывать» (правило репо, `AGENTS.md`).
- Блок не считается существующим, пока не пройдены ВСЕ шаги Фазы 4. Наполовину заведённый блок ломает генерацию страниц.
- Дизайн утверждает человек. Без явного «утверждаю» регистрация не начинается.

## Фаза 1 — замысел

Выясни у пользователя (коротко, 1 раунд вопросов):
- Роль блока: hero / narrative / roster / proof / cta / nav / conversion / explanation — и на каких страницах он будет жить.
- Контентная модель: какие поля должен менять редактор (заголовки, карточки, иконки, CTA…), сколько элементов (min–max).
- Референсы/пожелания по виду, если есть.

Проверь по `packages/blocks/src/registry.ts` и `ai/instructions/page-compose.md`, что задача действительно не решается существующим блоком — если решается, скажи об этом честно и остановись.

## Фаза 2 — дизайн в дизайн-системе

Перед вёрсткой загрузи скилл `impeccable` (Skill tool) — проектируй по его методологии, но в жёстких рамках дизайн-системы сайта:

Источники истины по стилю (прочитай перед первым макетом):
- `packages/styles/src/tokens.css` — цвета, шрифты, отступы, радиусы, тени, `--gradient-gold`.
- `packages/styles/src/typography.css`, `buttons.css` (`.c-btn`/`.ca-button`), `layout.css`, `formatting.css` (`.ca-gradient-text`).
- 2–3 существующих SCSS похожих блоков в `apps/web/src/styles/blocks/_*.scss` — паттерны именования и структуры.
- Живой сайт `http://localhost:4321/` и витрина блоков `/blocks`…`/blocks-9` — визуальный контекст, в котором блок должен смотреться родным.

Процесс:
1. Прототип — временная страница `apps/web/src/pages/_sandbox-block.astro` (подчёркивание = не попадает в роуты прод-сборки; в коммит не включать) либо standalone HTML в scratchpad с подключёнными токенами.
2. Итерируй в браузере: скриншоты desktop 1280 и mobile 375, hover/active-состояния, длинные тексты, min и max количество элементов.
3. Показывай пользователю варианты и правь до его явного утверждения. Новизна приветствуется, чужеродность — нет: токены, сетка и типографика только из дизайн-системы, никаких новых цветов/шрифтов без отдельного решения пользователя.

## Фаза 3 — утверждение

### Гейт «дизайн-система» (блокирующий, до показа на утверждение)

Блок не уходит на утверждение, пока не пройдены все пункты. Гейт проверяет субагент-ревьюер, не твоя самопроверка.

- **Ноль новых значений.** Цвета, шрифты, размеры, радиусы, тени, отступы — только токены из `packages/styles/src/tokens.css` / `source-foundation.scss`. Любое литеральное значение (`#hex`, `px` вне сетки) в `_<имя>.scss` = отказ. Нужное исключение оформляется как новый токен с обоснованием, а не как локальный литерал.
- **Числа и подсвеченные значения — по образцу.** Крупные числа, суммы, метрики и результаты расчётов оформляются типографикой существующих блоков (`metrics`, `pricing-cards`, `results-stats`): тот же размер, вес, трекинг, тот же способ выделения. Собственная типографика для «главной цифры» блока запрещена — именно на этом первый калькулятор выпал из стиля.
- **Градиент.** Только через `.ca-gradient-text`. На тёмных панелях `--gradient-gold` проходит через `#200000` и пропадает — обязателен override на сплошной amber. `:global()` в этих SCSS не работает, используй обычный потомочный селектор. Градиент никогда не вешается на значение, которое меняется в рантайме.
- **Side-by-side проверка.** Скриншот нового блока рядом со скриншотом эталонного блока той же роли, оба вьюпорта. Прикладывается к запросу на утверждение. Ревьюер отвечает на один вопрос: «эти два блока с одного сайта?» Ответ «нет» = отказ и возврат в Фазу 2.

### Утверждение

Зафиксируй с пользователем: финальный вид (скриншоты), имя типа блока (`kebab-case`), контентную модель, правила использования (когда брать этот блок, когда нет, идеальная плотность). Только после этого — Фаза 4.

## Фаза 4 — регистрация в библиотеке (полный чеклист)

Делай по образцу ближайшего существующего блока (найди его во всех этих файлах и повторяй структуру). Порядок:

1. **Схема** — `packages/blocks/src/schemas.ts`: zod-схема блока, добавить в union `PageBlock`.
2. **Каталог** — `packages/blocks/src/registry.ts`: `type`, `role`, `description`, `idealItems`, и главное — `aiGuidance`: когда использовать, когда НЕ использовать, чем не заменять. Это то, по чему генератор страниц будет принимать решения.
3. **Категория** — `packages/blocks/src/categories.ts`: добавить тип в подходящую категорию (Heroes/Grids/Proof/Content/Conversion/Navigation).
4. **Payload** — `apps/cms/src/collections/RoutableContent.ts`: block-конфиг с полями для админки (по образцу соседей). Затем применить схему БД: перезапустить cms dev с `PAYLOAD_DB_PUSH=true` (локально) и проверить, что блок появился в админке.
5. **Рендерер** — `apps/web/src/components/blocks/<Категория>/<Имя>Block.astro`. Стили ТОЛЬКО в `apps/web/src/styles/blocks/_<имя>.scss` — без inline-стилей и `<style>` в компоненте (правило репо, есть QA-гейт). Подключить SCSS через `@use "blocks/<имя>"` в `apps/web/src/styles/source-foundation.scss` (как соседние). Signup-ссылки — через общий резолвер, не хардкодить.
6. **Маппинг** — `apps/web/src/components/BlockRenderer.astro`: импорт + ветка для нового типа.
7. **Витрина** — добавить стори блока на страницу витрины (`apps/web/src/pages/blocks*`): все значимые варианты (min/max элементов, с медиа/без).
8. **Контракт** — `ai/contracts/block-contracts.md`: запись по шаблону; для net-new блока источник — утверждённый дизайн (скриншоты из Фазы 2), статус довести до `qa-ready`.
9. **Правила композиции** — `ai/instructions/page-compose.md`: параграф «Use `<тип>` for … Do not …» в стиле существующих. Это закон для /create-page.
10. Прототип из Фазы 2 удалить.

## Фаза 5 — валидация

Прогони и добейся зелёного:
```sh
npm run typecheck
npm --workspace @acme/web run build
npm run qa:no-inline-block-styles
npm run qa:no-hotlinks
npm run qa:block-root-attrs
```
Плюс: скриншот стори на витрине (desktop+mobile) и тестовая страница-черновик через `cms:upsert` с новым блоком (dry-run → write → открыть → скриншот → удалить черновик или оставить по желанию пользователя).

## Фаза 6 — сдача

Отчёт пользователю: имя типа, где смотреть (витрина + тестовый драфт), что записано в registry/contracts/page-compose, результаты QA. С этого момента `/create-page` может использовать блок. Напомни закоммитить изменения отдельным коммитом «add <block> block».
